# Архитектура онлайн-хаба VOVAN OS

Статус: целевая модель перед следующими этапами реализации. Документ не меняет конфигурацию серверов и не даёт AI-агентам произвольный доступ к ОС.

## Цель

Хаб должен быть единой онлайн-панелью для трёх серверов, проектов, сайтов, портов, доступов, задач и истории изменений. В обычной работе интерфейс остаётся простым: краткий обзор и понятные действия на первом экране; технические поля открываются внутри страниц проекта или сервера.

Сейчас сайт работает онлайн, но сборщик формирует снимки примерно раз в минуту. Часть настроек, избранного, личных проектов и задач хранится в localStorage конкретного браузера. Поэтому одинакового состояния на телефоне и ПК нет, а слово «локально» в интерфейсе описывает браузерные данные, а не размещение сайта.

## Как понимать «в реальном времени»

Обновлять каждое поле каждую секунду и опрашивать все источники одинаково часто не нужно. Целевые интервалы:

| Данные | Целевое обновление | Поведение интерфейса |
|---|---:|---|
| События задач, AI-агентов, деплоев и аварий | сразу, обычно до 2 секунд | Сервер отправляет событие открытым SSE-потоком |
| Доступность серверов и базовая нагрузка | 5–10 секунд | При нескольких пропущенных проверках состояние становится «Нет связи» |
| Сервисы и контейнеры | 15–30 секунд | В карточках виден статус и время последней проверки |
| Порты, домены, сертификаты, карта зависимостей | 1–5 минут и после изменений | Показываются источник и время инвентаризации |
| Каталог GitHub и метаданные проектов | по webhook или раз в несколько минут | Новый репозиторий можно добавить в каталог без деплоя |

Для отправки обновлений в открытую страницу использовать Server-Sent Events (SSE). Для изменения настроек и создания задач использовать HTTPS API под существующим входом админки. Потеря SSE автоматически запускает повторное подключение и показывает время последнего успешного события.

## Экран и навигация

Главная показывает три карточки серверов, до пяти важных предупреждений, избранные проекты, активные/заблокированные задачи и кнопку добавления проекта. Статус каждого блока сопровождается последним временем обновления. Виджеты главной можно включать, скрывать и менять местами.

Боковое меню можно свернуть, раскрыть и изменить по ширине; пользователь может менять порядок и видимость разделов. Настройки меню и главной хранятся в профиле на сервере и синхронизируются между устройствами. На телефоне меню становится компактной панелью или выдвижной навигацией.

Карточка проекта в списке занимает мало места и показывает только:

- название и короткое назначение;
- жизненный статус и техническое здоровье;
- основной сервер и текущий этап;
- следующий шаг или блокер;
- свежесть данных и быстрые действия «Открыть» и «Создать задачу».

По нажатию открывается отдельная страница проекта, а не длинный прокручиваемый модал. Вкладки: «Обзор», «Задачи», «Сервисы и данные», «Сайты и доступ», «Деплои», «Связи», «История». Служебные имена, каталоги и таблицы остаются во вложенных разделах.

## Жизненный цикл проекта

Проект и репозиторий — разные объекты: у проекта может быть несколько репозиториев и окружений, а репозиторий без запущенного сервиса всё равно виден в каталоге.

Предлагаемые статусы проекта: «Идея», «Запланирован», «В работе», «Пауза», «Работает», «Архив», «Не нужен». Решение «показывать на главной» хранится отдельно от статуса. Скрытие не удаляет проект или его данные; архив и «Не нужен» доступны через фильтр.

Добавление проекта проходит короткую форму: новый проект или импорт GitHub-репозитория; название и цель; репозитории; сервер/окружение; домены; статус; следующий шаг. Связи и обнаруженные сервисы можно подтвердить позже. При импорте GitHub проект не считается развёрнутым автоматически.

## Предупреждения и неподключённые источники

Каждая проблема должна объяснять ситуацию, а не только показывать красный текст. Запись предупреждения содержит источник, время последнего события, симптом, влияние, уверенность диагностики и следующий рекомендуемый шаг.

Для примера с аналитикой EEKLERA карточка сообщает, что события аналитики не поступали с 6 октября, показывает, какие данные доступны вместо них, и предлагает проверяемые шаги: проверить подключение источника событий, адрес приёма и время последнего успешного запроса. Пока события не вернулись, просмотры из журнала Nginx помечаются как приблизительная замена. Если причина не подтверждена данными, интерфейс так и пишет, вместо выдачи догадки за факт.

Действия у предупреждения: «Проверить источник», «Что нужно предоставить», «Создать задачу» и «Скопировать контекст для GPT/Claude». Контекст включает только нужные несекретные факты, ожидаемый результат и ограничения. Секреты не копируются.

## Серверы, доступ и связи

Страница сервера содержит ресурсы, сервисы по проектам, контейнеры, открытые порты, домены и маршруты, сертификаты, резервные копии и список зависимых проектов. Страница портов связывает внешний порт с процессом, сервером и политикой firewall.

Реестр адресов различает «Открыт для всех», «Требует вход», «Только внутренний», «Не отвечает» и «Не проверено». Классификация строится по конфигурации маршрутов и обычной внешней HTTP-проверке. Проверки не пытаются обходить авторизацию или подбирать пароли.

Карта показывает серверы, проекты, репозитории, сервисы, базы и домены. При выборе узла подсвечиваются связи и проекты, которые потеряют функцию, если узел недоступен.

## Онлайн-архитектура

1. Браузер открывает интерфейс по HTTPS и проходит существующую авторизацию админки.
2. Новый Hub API на главном сервере отдаёт данные, принимает изменения каталога/настроек/задач и публикует события SSE. API слушает только loopback; наружу используется текущий HTTPS-маршрут за авторизацией.
3. У API есть отдельная база и отдельная роль БД. В ней хранятся настройки интерфейса, ручные заметки, жизненный статус, задачи и аудит действий. Инвентаризация серверов остаётся read-only и не смешивается с секретами приложений.
4. Сборщик на главном сервере получает разрешённые read-only показатели трёх серверов и пишет их с временными метками. Частые метрики и медленная инвентаризация запускаются разными интервалами.
5. События проекта, подключения источника и выполнения задачи сразу передаются открытым страницам. Для восстановления после перезапуска клиент получает последний снимок и продолжает поток.

До реализации нужно проверить путь существующей авторизации, правила резервного копирования и способ безопасной доставки серверного API. Установка новых systemd-служб, изменение Nginx и работа с SSH-доступом требуют отдельного согласования и отдельного плана отката.

## AI-задачи и безопасность

Задача хранит проект, цель, контекст, ограничения, назначенного агента, состояние, ссылки на изменения и журнал шагов. Статусы: «Новая», «Нужна информация», «В очереди», «В работе», «Заблокирована», «Ожидает проверки», «Готово».

AI-агент получает только выбранный проект и задачу. Для изменений кода он работает в отдельной ветке, запускает проверки и возвращает Pull Request. Доступ к серверам по умолчанию только для чтения через разрешённые сборщики. Произвольные root-команды, VPN-ключи, пароли и секреты модели недоступны. Деплой, изменение сетевых правил, служб, Nginx, SSH и базы выполняются отдельным явно одобренным действием с журналом и возможностью отката.

## Этапы реализации

1. Уже сделано: инвентаризация Германии, актуальность данных и статусы серверов.
2. Онлайн-основа: API, отдельное хранилище, поток событий, согласованный сбор метрик и видимый возраст каждого источника.
3. Главная: три сервера, реальные предупреждения, избранные проекты, незавершённые задачи, быстрый импорт и создание проектов.
4. Каталог и проект: компактные карточки, жизненный цикл, отдельная страница проекта, синхронные между устройствами настройки.
5. Операционные разделы: все порты, доступ к сайтам, схема связей и последствия отказа сервера.
6. Очередь AI-задач: OpenAI/Claude, рабочая ветка и Pull Request; затем отдельно — одобряемые действия деплоя.

Каждый этап — отдельный Pull Request с проверками, коротким описанием поведения и возможностью откатить отдельный merge-коммит.
